title: Projects
description: Learn how Istok scopes durable agent state to a repository.
---

A project is the boundary around the durable state Istok keeps for a repository.

You register a repository as a project once. The usual way is to ask your coding agent:

> Register this project in Istok.

The agent registers the directory it was started in through MCP. From the terminal, the same is done with:

```sh
istok init
```

From that point, coding agents connected through MCP can identify the project they are working in and access its Istok state.

## Project-scoped state

Istok keeps work associated with the project rather than with a particular conversation or coding agent.

A project can contain:

* tasks and their dependencies;
* project context and instructions;
* project knowledge;
* progress recorded while work is in progress;
* runs representing attempts to complete tasks;
* validation results and other execution evidence.

This gives agents a shared place to inspect what is happening in the repository.

## Repository identity

Istok identifies the project from the repository an agent is working in.

This means a globally configured `istok mcp` connection can be reused across multiple repositories. The agent does not need a separate MCP server configuration for every project.

Only repositories that you explicitly register with Istok become Istok projects.

Istok does not create marker files in your repository. The association between a directory and its project is stored in the Istok database.

## Nested projects

A project can live inside another project's directory. For example, a monorepo can be one project while an application inside it is a separate project:

```text
~/work/platform            → project "platform"
~/work/platform/apps/web   → project "web"
```

When Istok resolves the current project, the closest project wins. Work started in `~/work/platform/apps/web` or any directory below it belongs to `web`; work anywhere else inside `~/work/platform` belongs to `platform`.

Two active projects cannot share exactly the same directory.

## One project, multiple sessions

Project state is independent of an individual agent session.

For example, you might ask an agent to begin implementing a feature today and continue the work in a new session tomorrow.

The new session can inspect the same project and recover the relevant Istok state instead of relying only on the previous conversation.

The same applies when different coding agents work with the repository.

## Project context

A project can also contain durable information that should remain available beyond a single task.

This is useful for knowledge such as:

* architectural decisions;
* important repository conventions;
* constraints that agents should remember;
* implementation notes that remain relevant to future work.

Task-specific information can stay with the task, while longer-lived knowledge remains available at the project level, either as short [context](/docs/en/how-istok-works/context) records or as reviewed [knowledge](/docs/en/how-istok-works/knowledge) items.

## Inspecting a project

Most project operations happen through the coding agent, but the CLI can also be used to inspect registered projects when needed.

For example:

```sh
istok project list
```

and:

```sh
istok project show
```

The [web UI](/docs/en/guides/web-ui) shows the same projects in the browser, with task counts, running and stale runs, and recent activity:

```sh
istok ui
```

The full command surface is documented in the [CLI reference](/docs/en/reference/project).

## Deleting a project

Deleting a project removes it from the active project list and releases its directory, but keeps its tasks, runs, and history. It never touches the repository files, and it can be undone with `istok project restore`. See [project](/docs/en/reference/project#delete-a-project).
