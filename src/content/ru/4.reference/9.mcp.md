`istok mcp` запускает MCP-сервер, с которым общается ваш кодинг-агент. Здесь перечислены его флаги и все инструменты, которые он предоставляет. Чтобы подключить агента, пройдите [быстрый старт](/docs/ru/getting-started/quick-start).

## Запуск сервера

```sh
istok mcp --actor-id codex --actor-name "Codex"
```

Сервер говорит на MCP через стандартные ввод и вывод: MCP-клиент сам запускает команду и общается с процессом напрямую. Stdout занят протоколом.

| Флаг | По умолчанию | Назначение |
| --- | --- | --- |
| `--actor-id` | генерируется при старте | Постоянный ID агента. Также `ISTOK_AGENT_ID`. |
| `--actor-name` | `MCP Agent` | Отображаемое имя агента. Также `ISTOK_AGENT_NAME`. |
| `--profile` | `worker` | Профиль инструментов: `worker`, `supervisor` или `admin`. |
| `--database` | пользовательская директория данных | Путь к базе SQLite. Также `ISTOK_DATABASE`. |

Флаг важнее своей переменной окружения. Для работы через MCP нужна база в файле. См. [Настройка](/docs/ru/reference/configuration).

## Область проекта

Каждый процесс сервера определяет проект по директории, в которой его запустили, и сохраняет эту область до конца работы. При вложенных проектах побеждает ближайший.

Инструменты не принимают другой корень проекта, корень файловой системы или селектор проекта, так что агент не может направить вызов в другой проект. Поэтому же одна глобальная настройка MCP подходит для всех зарегистрированных репозиториев: каждый запущенный процесс обслуживает репозиторий, в котором его запустили.

Если директория ещё не зарегистрирована, агент может вызвать `project_init` — он доступен в любом профиле. Инструмент регистрирует директорию запуска сервера, принимает необязательное имя проекта и возвращает существующий проект, если директория уже зарегистрирована. Может ли агент делать это сам, решают ваши инструкции для агента; рекомендуемые инструкции из [быстрого старта](/docs/ru/getting-started/quick-start) регистрируют репозиторий только по вашей просьбе.

## Исполнитель

У каждого процесса сервера ровно один исполнитель (actor): логический агент, который делает работу, а не конкретный разговор. Он фиксируется при старте, и отдельные вызовы инструментов не могут его переопределить.

| Значение   | Пример  | Назначение                            |
| ---------- | ------- | ------------------------------------- |
| Actor ID   | `codex` | Постоянный машиночитаемый идентификатор |
| Actor name | `Codex` | Понятное человеку имя                 |

Запуски записывают своего исполнителя, проверки и артефакты тоже. Дайте каждому агенту свой постоянный ID, например `claude` для Claude Code и `codex` для Codex, — тогда их работу можно различить и после перезапусков. Без `--actor-id` Istok генерирует уникальный идентификатор только для этого процесса.

Исполнитель важен и для владения: сигналы активности, восстановление и завершение запуска проверяются по исполнителю, которому принадлежат запуск и его текущая аренда. См. [Несколько агентов в одном проекте](/docs/ru/guides/multiple-agents).

## Инструменты

### Проект

```text
health
project_current
project_init
```

### Задачи

```text
task_create
task_update
task_list
task_show
task_ready
task_comment
task_progress
task_block
task_unblock
task_dependency_add
task_dependency_remove
```

### Контекст

```text
context_add
context_update
context_enable
context_disable
context_list
context_show
context_search
context_package
context_preview
context_doctor
```

`context_preview` показывает ограниченный контекст, который получит взятие задачи, не создавая запуск. `context_doctor` сообщает о проблемах с ростом и жизненным циклом контекста. См. [`istok context`](/docs/ru/reference/context#ограниченная-сборка-контекста).

### Знания

```text
knowledge_catalog
knowledge_search
knowledge_show
knowledge_read
knowledge_create
knowledge_distill
knowledge_update
knowledge_review
knowledge_promote
knowledge_supersede
```

Каталог и поиск возвращают метаданные и короткие фрагменты; `knowledge_show` и `knowledge_read` возвращают одну заметку целиком. Проверка, утверждение и замена — отдельные явные шаги. Экспорт в файл доступен только через CLI.

### Поиск по коду

```text
index_status
index_rebuild
search
graph_symbol
graph_neighbors
graph_path
```

`search` и чтение графа сначала проверяют актуальность индекса. Эти инструменты не позволяют переопределить проект или корень репозитория.

### Запуски и проверки

```text
task_claim
run_list
run_show
run_exec
run_validate
run_heartbeat
run_artifact_list
run_artifact_verify
run_recover
run_finish
task_complete
```

`task_claim` собирает ограниченный контекст (сохранённый контекст, найденный код и сводку знаний) и создаёт запуск по тому же процессу, что и CLI. В ответе есть запуск и точный снимок контекста, сохранённый для него, так что агенту не нужно вручную искать и собирать стартовый контекст.

`run_exec` и `run_validate` работают так же, как их аналоги в CLI. Вызывающий передаёт команду и ограниченные опции выполнения, но не окружение: управляемые команды получают разрешённое окружение, которое сохранил сервер, плюс служебные переменные Istok. См. [`istok run`](/docs/ru/reference/run).

Для работы, которая шла не через `run_exec` или `run_validate`, эти инструменты задним числом записывают выполнения и заявленные (attested) проверки:

```text
execution_start
execution_finish
validation_record
```

## Профили

Профили определяют, какие инструменты получает агент. Для стандартной настройки они не нужны: по умолчанию используется `worker`.

```sh
istok mcp --profile supervisor --actor-id claude --actor-name "Claude Code"
```

* **`worker`** — обычная работа: просмотр проекта и `project_init`, задачи, контекст вместе с предпросмотром и диагностикой, знания, поиск по коду, взятие задач, выполнение команд и проверки, восстановление запусков и завершение задач.
* **`supervisor`** — всё из `worker` плюс `run_abandon`, чтобы прервать активный запуск, оставив задачу открытой.
* **`admin`** — всё из `supervisor` плюс:

```text
project_list
project_rename
project_rebind
project_delete
project_restore
task_delete
task_restore
context_archive
```

`project_rebind` и `project_restore` привязывают проект к директории запуска сервера. `project_delete` требует повторить ID проекта для подтверждения.

Восстановить запуск можно в любом профиле, но только если вызывающий — исполнитель, которому принадлежит аренда; перехватить чужой запуск восстановлением нельзя. Используйте расширенные профили, только когда они действительно нужны агенту.

## Результаты

Результаты MCP — версионированные структурированные обёртки (`schema_version: "1"`); результаты запусков используют `"2"`, а форматы поиска и графа несут собственные версии контрактов. Пустые коллекции возвращаются как `[]`, никогда как `null`. См. [Вывод JSON](/docs/ru/reference/json-output).

## Настройка MCP и инструкции

Настройка MCP делает инструменты доступными и фиксирует проект и исполнителя. Она не говорит агенту, когда создавать задачу, когда маленькую просьбу можно не отслеживать, можно ли регистрировать репозиторий и как проверять работу. Эти правила задаются в инструкциях для агента; рекомендуемый стартовый набор есть в [быстром старте](/docs/ru/getting-started/quick-start).
