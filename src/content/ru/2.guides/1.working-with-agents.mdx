С Istok вы работаете через разговор с агентом. Здесь показано, что говорить в типичных ситуациях и что Istok каждый раз записывает, — чтобы вы знали, что найдёт следующая сессия.

В примерах проект `acme-api`, агенты Claude Code и Codex. Предполагается, что агент уже подключён и получил инструкции из [Быстрого старта](/docs/ru/getting-started/quick-start).

## Начать задачу

Опишите работу так, как обычно. Упоминать Istok не нужно.

<Prompt>GET /orders/{"{id}"} отдаёт 500, если заказа нет. Для неизвестных заказов должен быть 404, остальные ошибки пусть остаются 500.</Prompt>

**Что записывает Istok:** задачу, например #18 «Return 404 for missing orders», с описанием и критериями приёмки. Перед тем как писать код, агент начинает задачу: открывается запуск под его идентификатором исполнителя, и Istok сохраняет, какой именно контекст агент получил.

На вопрос или правку в одну строку агент просто ответит. Задачи нужны для работы, к которой стоит вернуться позже.

## Узнать, что происходит

Спросите о проекте, вместо того чтобы листать старые чаты.

<Prompt reply="Открыто 3 задачи, 2 заблокированы. По #20 идёт активный запуск Codex; #19 ждёт #10.">Что сейчас открыто в Istok по этому проекту?</Prompt>

<Prompt>Что было с задачей 18? Кто над ней работал и почему не удалась первая попытка?</Prompt>

**Что записывает Istok:** ничего. Агент только читает задачи, их историю и запуски. В терминале то же самое показывают `istok task list` и `istok task show 18`.

## Продолжить в новой сессии

Перед тем как сессия закончится или её контекст сожмётся, агент записывает **передачу дел**: что сделано, где он остановился, какие решения принял и какой следующий шаг. С `istok hooks install claude --stop` (или `codex`) агенту напоминают записать её, если он останавливается посреди задачи.

Новый чат ничего не знает о старом, но с установленными хуками ему сразу при старте показывают прерванную работу. Иначе укажите ему задачу:

<Prompt>Продолжи задачу 20.</Prompt>

<Prompt>Продолжи незаконченную работу над повторами платежей.</Prompt>

**Что записывает Istok:** агент снова начинает задачу и получает последнюю передачу дел, свежие заметки и прошлые запуски. Если его предыдущий запуск ещё активен, он продолжает этот запуск; если нет — начинается новый запуск со свежим контекстом. В терминале ту же прерванную работу выводит `istok resume`.

## Закончить с доказательствами

Инструкции и так требуют от агента проверить результат перед закрытием задачи. Но вы можете прямо сказать, что считать доказательством.

<Prompt reply="go test ./... прошёл (проверка записана). Задача 18 выполнена.">Прогони все тесты через Istok и закрой задачу, только если они пройдут.</Prompt>

**Что записывает Istok:** проверку с командой, результатом и выводом, привязанную к запуску. Задача закрывается со ссылкой на эту проверку, так что за «готово» стоят доказательства. Если проверка не прошла, неудача остаётся в истории, а задача — открытой.

Проверку, сделанную в другом месте, например в CI или вручную, тоже можно записать; Istok помечает её как сообщённую агентом, а не выполненную самим Istok. Если проверять нечего, например при правке документации, агент должен явно объяснить, почему закрывает задачу без проверки. Эта причина тоже записывается.

## Запомнить правило

Если вы поправили агента и хотите, чтобы поправка сохранилась, попросите его запомнить правило:

<Prompt>Запомни для этого проекта: поля публичного API пишутся в snake_case.</Prompt>

Агент сохранит его как правило проекта, а позже по вашей просьбе найдёт и изменит сохранённые правила. В терминале правило можно добавить самому:

```sh
istok context add "API naming convention" --kind decision \
  --body "Public API fields use snake_case."
```

Правило — это короткая запись контекста с видом: `note`, `decision`, `constraint` или `instruction`. Режим доставки определяет, когда агент её получит:

- **`always`** — её получает каждый запуск. По умолчанию для инструкций. Делайте такие записи короткими: они занимают место в каждом запуске.
- **`ranked`** — попадает в запуск, когда подходит к задаче. По умолчанию для остальных видов.
- **`manual`** — автоматически не попадает никогда, только по явному запросу по ID.

`istok context list` показывает, что сохранено в проекте; `istok context disable` выключает инструкцию, не удаляя её.

## Сохранить длинные знания

Знания — для материалов, слишком длинных, чтобы отправлять их с каждой задачей: как устроен возврат денег, почему у заказов UUIDv7, как ротировать ключи. Каждый запуск получает только заголовки и краткие описания актуальных записей, а полный текст агент читает, когда он нужен задаче.

Обычно знания создают в конце исследования (для этого нужен `--tools full`):

<Prompt>Оформи то, что ты выяснил про возврат денег, как черновик знаний, с этой задачей в качестве источника.</Prompt>

Новая запись — это **черновик**. Агенты опираются на неё только после того, как вы проведёте ревью и переведёте её в **актуальные**:

```sh
istok knowledge show ID
istok knowledge review ID --expected-revision 1 \
  --note "Checked against internal/refunds on main"
istok knowledge promote ID --expected-revision 2
```

Правка черновика сбрасывает ревью. Актуальные записи редактировать нельзя: когда факты меняются, старую запись заменяет новый черновик, прошедший ревью. `istok knowledge list` и `istok knowledge search` показывают, что уже есть.

## Узнать, что увидел агент

Если агент проигнорировал правило, выясните, получил ли он его.

- `istok context preview 18` показывает, что получит задача 18 при старте, не начиная запуск.
- `istok run show RUN_ID` показывает контекст, сохранённый для запуска, рядом с его командами и проверками.
- `istok context doctor` сообщает о просроченных, слишком больших и повторяющихся записях.

## Несколько агентов в одном проекте

Claude Code и Codex могут работать над одним проектом. У них общие задачи, история и доказательства, но не разговоры.

**Дайте каждому агенту идентификатор.** `--actor-id`, указанный при подключении агента, — его постоянный идентификатор, а `--actor-name` — имя, под которым он показывается. Запуски и записи истории помечаются им, поэтому в задаче видно, что первую попытку сделал Codex, а вторую — Claude Code. Если не указать `--actor-id`, каждый процесс MCP получает новый идентификатор, и перезапущенный агент не сможет продолжить собственный запуск.

**Передайте работу.** Писать отдельный документ не нужно: в задаче уже есть описание, заметки, прошлые запуски и передача дел.

<Prompt>Прекрати работу над задачей 18, я передам её Claude Code.</Prompt>

Агент записывает передачу дел и завершает свой запуск, оставляя задачу открытой. Затем скажите другому агенту:

<Prompt>Возьми задачу 18 в Istok. Сначала прочитай передачу дел.</Prompt>

Другой агент сразу начинает задачу и получает передачу дел.

**Если запуск брошен.** Агент, который просто замолчал, свой запуск не завершил. Активный запуск держит аренду, и каждый вызов Istok агентом её продлевает. Если агент молчит 15 минут, аренда истекает, и запуск становится **зависшим**. Тогда:

- **тот же агент** продолжает свой запуск следующим вызовом, например когда вы попросите его продолжить задачу;
- **другой агент**, начиная задачу, закрывает зависший запуск как `abandoned` и начинает новую попытку;
- **вы** можете сразу прервать запуск командой `istok run abandon`. Запуск остаётся в истории, а задача освобождается.

**Параллельная работа.** Задачу с живым запуском не может взять другой агент, а задача, которая зависит от незаконченной, не попадает в список готовых.

<Prompt>Покажи задачи, которые готовы к работе.</Prompt>

<Callout type="warning" title="Istok согласует задачи, а не файлы">Два агента в одной рабочей копии всё равно могут править одни и те же файлы. Давайте параллельным агентам несвязанные задачи.</Callout>

## Если агент забывает про Istok

Иногда агент начинает писать код, не создав задачу. Обычно не хватает одного из трёх:

- **MCP-сервер не подключён.** Проверьте командой `/mcp` в Claude Code или в настройках MCP вашего агента.
- **Проект не зарегистрирован.** Выполните `istok project list` или попросите агента зарегистрировать проект.
- **Инструкций нет или они слишком слабые.** Агент не знает, когда пользоваться инструментами.

Чтобы поправить его на ходу:

<Prompt>Используй для этого Istok: найди или создай задачу, начни её и запиши проверку перед тем, как закончить.</Prompt>

Если это повторяется, замените короткий блок из быстрого старта этой подробной версией в глобальных инструкциях (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` или User Rules в Cursor):

```md
## Работа с Istok

Istok — основной источник долговременного состояния проекта для нетривиальной работы в репозиториях, зарегистрированных в Istok.

Используй MCP-инструменты Istok как основной интерфейс для состояния проекта, задач, контекста, запусков, проверок и поиска по репозиторию. Переходи на CLI Istok, только если MCP недоступен или не даёт нужной операции, и в этом случае предпочитай структурированный вывод.

### Перед нетривиальной работой

1. Определи текущий репозиторий или корень проекта.
2. Найди проект в Istok. Если подходит несколько проектов, используй самый конкретный. Никогда не переключайся молча на другой проект.
3. Если проект зарегистрирован, загрузи его включённые инструкции и используй ограниченный контекст, который Istok собирает для задачи. Не загружай разом весь сохранённый контекст и все знания.
4. Проверь существующие задачи, если работа уже может быть оформлена задачей.

Если репозиторий не зарегистрирован, сообщи об этом пользователю, не регистрируй его автоматически и продолжай без Istok, пока пользователь не попросит его зарегистрировать.

### Задачи

Создавай задачу для новых функций, исправлений ошибок, рефакторинга, миграций, исследований и других нетривиальных изменений. Не создавай задачи для вопросов, объяснений, мелких правок и быстрого чтения кода.

1. Используй подходящую задачу или сам создай узкую, не дожидаясь просьбы.
2. Начни задачу и веди текущую попытку в запуске.
3. Записывай заметный прогресс, блокеры, зависимости и решения по ходу работы.
4. Перед тем как остановиться или сжать контекст, запиши передачу дел.
5. Проверь результат и запиши команды, результаты и подтверждения.
6. Закрывай задачу только после того, как результат реализован и проверен. Одной реализации недостаточно.

### Контекст и знания

Следуй включённым инструкциям проекта, которые возвращает Istok. Используй контекст для коротких долговременных решений, ограничений и соглашений. Используй знания для более длинной актуальной информации — заметок об архитектуре, runbook'ов: находи их через каталог или поиск и читай только то, что относится к делу.

Извлекай знания в черновик с указанием источника, сверяй с текущим кодом, записывай ревью и утверждай только после ревью. Заменяй знания, которые устарели.

Никогда не записывай управляемое Istok содержимое в корень проекта. Не копируй состояние активных задач в TODO-файлы, планы или документы со статусом, если пользователь не просит.

### Поиск и завершение

Предпочитай поиск и граф Istok для поиска кода, но сверяй детали с текущими исходниками перед изменениями.

Никогда не утверждай, что проверка прошла, если она не была успешно выполнена. Если какую-то проверку выполнить не удалось, скажи об этом, а не выдавай работу за полностью проверенную. Держи Istok в актуальном состоянии, чтобы пользователю не приходилось делать это самому.
```

Если в репозитории все участники должны работать по одному процессу, можно также закоммитить сокращённую версию этих правил в `AGENTS.md` или `CLAUDE.md` проекта.
